# Tracker secrets in the OS keychain: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Store Linear, Jira, GitLab, Azure DevOps (and the coming Plane) secrets in the OS keychain instead of `0600` files, migrating each old file once and then deleting it, in both the Tauri app and Gespan Native.

**Architecture:** A new shared crate `crates/tracker-secrets` (package `gespan-tracker-secrets`) owns the keychain entry names, the one-time migration from the old file and the delete path. `src-tauri/src/{linear,jira,gitlab,azure_devops}.rs` and `crates/gespan-core/src/inbox/{linear,jira,gitlab,azure_devops}.rs` replace their file I/O with calls into it, so both apps read and write the very same entries.

**Tech Stack:** Rust, `keyring` 3.6 (already a dependency of both apps, same per-OS features), `tempfile` for tests.

**Spec:** GitHub issue #102 (approved design). Working rules: #60.

## Global Constraints

- Secrets for Linear, Jira, GitLab, Azure DevOps and Plane go through `keyring`.
- Old files are migrated once, then deleted: `linear-token`, `jira-config.json`, `gitlab-config.json`, `azure-devops-config.json` in the app data directory.
- Both apps must use the same keychain entries.
- No secret appears in logs or error strings.
- Gespan names only (`src/test/legacyNames.test.ts`).
- Hotspot files (`Cargo.toml` dependency lists, lock files): small additive edits; lock files regenerated by cargo, never by hand.
- New shared crates go under `crates/` (like `mobile-link`, `keep-awake`).

## Decisions (my calls)

- **Entry names.** Service `dev.gespan.trackers`; account `<tracker>:<data dir>`, for example `linear:/Users/me/Library/Application Support/dev.gespan.desktop`. This follows the existing mobile identity entry (`dev.gespan.mobile`, `desktop:<path>`). Keying by data directory keeps today's behaviour exactly: when Native runs in Gespan-data mode it shares the Tauri data directory and so the same secrets; dev-data Native keeps its own, as it does with files today.
- **Stored value.** The keychain value is exactly what the old file held (the raw Linear key; the JSON object for Jira, GitLab and Azure DevOps). Migration moves bytes, and the existing parsers and validation stay unchanged. The site URL and email ride along with the token; they are not secret, but keeping one entry per tracker avoids a second store.
- **Migration order.** Write to the keychain first, then delete the file. If the keychain write fails, the file is kept and its value is still returned so the tracker stays connected; the next read retries. A secret is never lost to a half-done migration. If the keychain already has a value, it wins and any leftover file is deleted.
- **Plane.** `Tracker::Plane` is defined now (no old file) so #100 uses the same store; no Plane provider code is added here.
- **Tests and the real keychain.** Tests never touch the OS keychain. The crate ships a `testing` feature with an in-memory `keyring` credential builder (persistent across `Entry` values, unlike `keyring::mock`) plus a switch to make writes fail. The crate's own tests and the `gespan-core` / `src-tauri` tests install it.

## Review Focus

1. A keychain that is locked or unavailable (Linux without a Secret Service) during migration: the old file must survive and the tracker stay connected. Covered by `failed_keychain_write_keeps_the_file` (Task 1).
2. The file and the keychain both hold a value (a crash between write and delete): the keychain wins and the file is removed. Covered by `keychain_value_wins_and_leftover_file_is_removed` (Task 1).
3. Disconnect after migration must clear the keychain entry *and* any file, or the token reappears on the next read. Covered by `delete_clears_keychain_and_file` (Task 1) and `disconnect_clears_the_keychain_entry` (Task 2).
4. Two data directories (dev Native vs Tauri) must not overwrite each other's secrets. Covered by `data_directories_are_isolated` (Task 1).
5. Error strings from a failing keychain must not contain the secret. Covered by `errors_never_contain_the_secret` (Task 1).

### Task 1: `gespan-tracker-secrets` crate

**Files:**
- Create: `crates/tracker-secrets/Cargo.toml`, `crates/tracker-secrets/src/lib.rs`, `crates/tracker-secrets/src/testing.rs`
- Modify: root `Cargo.toml` (workspace `members`), `.github/workflows/native.yml` (add `crates/tracker-secrets/**` to the PR paths, because `gespan-core` now depends on it)

**Interfaces:**
- Produces:
  - `pub enum Tracker { Linear, Jira, Gitlab, AzureDevOps, Plane }` with `fn key(self) -> &'static str` (`linear`, `jira`, `gitlab`, `azuredevops`, `plane`) and `fn legacy_file(self) -> Option<&'static str>`.
  - `pub const SERVICE: &str = "dev.gespan.trackers";`
  - `pub fn account(tracker: Tracker, data_dir: &Path) -> String`
  - `pub fn read(tracker: Tracker, data_dir: &Path) -> Result<Option<String>, String>`: keychain value, else migrates the old file; returns `None` when neither exists.
  - `pub fn write(tracker: Tracker, data_dir: &Path, value: &str) -> Result<(), String>`: keychain write, then removes any old file.
  - `pub fn delete(tracker: Tracker, data_dir: &Path) -> Result<(), String>`: removes the entry (missing is fine) and any old file.
  - feature `testing`: `testing::use_memory_keychain()` (idempotent, process-wide), `testing::stored(tracker, dir) -> Option<String>`, `testing::fail_writes(tracker, dir, bool)`.

- [ ] **Step 1: Write the failing tests** in `src/lib.rs` `#[cfg(test)]` (dev-dependency on itself with `testing`, plus `tempfile`):
  - `migrates_the_old_file_once_and_deletes_it`: write `linear-token` = `"lin_api_x\n"`; `read` returns `Some("lin_api_x\n")`; file gone; `stored` equals it; a second `read` still returns it.
  - `keychain_value_wins_and_leftover_file_is_removed`: keychain `new`, file `old`; `read` = `new`; file gone.
  - `failed_keychain_write_keeps_the_file`: `fail_writes(true)`; `read` returns the file value; file still present; `stored` is `None`; after `fail_writes(false)` the next `read` migrates.
  - `write_replaces_the_old_file`: file present; `write("v")`; file gone, `stored` = `v`.
  - `delete_clears_keychain_and_file`: both present; `delete`; `read` = `None`; `delete` again is `Ok`.
  - `data_directories_are_isolated`: two temp dirs, different values.
  - `errors_never_contain_the_secret`: `fail_writes(true)`; `write(secret)` is `Err` and the message does not contain `secret`.
  - `account_names_match_the_shared_contract`: `account(Tracker::Jira, "/d")` = `"jira:/d"`; legacy files map to the four names above, `Plane` → `None`.
