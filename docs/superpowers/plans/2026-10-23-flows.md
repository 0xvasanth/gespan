# Flows Implementation Plan (state machine)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let users draft a reusable, deterministic orchestrator (a **Flow**). A Flow is a state machine whose agent states each run in a fresh, isolated session on any supported harness. States receive only the inputs explicitly linked to them, and return typed outputs that choose the next state.

**Architecture:** A Flow definition has inputs, states and ordered transitions. A small app-side controller (`flowRunner.ts`) runs one state at a time, starting the run from the definition snapshot taken when the run began.

For each agent state, the controller:

1. Renders the state's brief from its bindings.
2. Appends an output contract asking for a final fenced JSON block.
3. Launches a fresh session through the same path automations use, with all states of a run sharing one git worktree.
4. Parses and validates the JSON, retrying once in the same session if it's invalid.
5. Evaluates the transitions to pick the next state.

Approval states pause the run for the user. Every state visit is persisted, so runs survive restarts and can resume from any state. The orchestration engine is **not** used or modified.

**Tech Stack:** Rust + rusqlite (JSON-blob rows, same pattern as `automations.rs`), React 19 + TS, Vitest.

**Spec:** Decisions from the 2026-10-23 conversation, recorded under Design Decisions below. The user approved all four: a JSON output contract, a shared worktree per run, sequential states with loops in v1, and Kiro handled separately.

## Design Decisions

- **Each agent state gets a fresh session**, with no chat history from earlier states. It sees only its rendered brief. That isolation is what makes a run repeatable.
- **One worktree per run.** The first agent state creates it (`workspaceMode: "worktree"`, `worktreeBase: "HEAD"`), and the runner records the session's resulting `worktreeCwd` on the run. Later states get `worktreeCwd` set to it, so they build on earlier file changes.
- **Bindings syntax:** `{{inputs.<name>}}` and `{{states.<id>.outputs.<field>}}`. A binding reads the **latest** visit of that state. A trailing `?` (for example `{{states.test.outputs.failures?}}`) makes it optional: it renders `""` when the state hasn't produced that output yet. A non-optional binding with no value fails the visit with `Binding states.<id>.outputs.<field> has no value yet`. Rendering:
  - strings as-is
  - numbers and booleans via `String()`
  - `string[]` as `- item` lines
- **Output contract:** each state declares `outputs: {name, type: "string"|"number"|"boolean"|"string[]", description}[]`. The runner appends this exact footer (field lines generated) to the brief:

  ```
  ---
  When you are done, end your reply with one fenced ```json block containing exactly these fields:
  - <name> (<type>): <description>
  Do not add other fields.
  ```

  The runner parses the **last** ```json fenced block in the final reply text. Extra fields, missing fields and wrong types are errors. On error it sends one follow-up in the same session:

  ```
  Your JSON block was invalid: <errors joined by "; ">. Reply with only the corrected ```json block.
  ```

  If the reply still fails, the visit ends `failed` with error `Output contract not met: <errors>`. A state with zero outputs skips parsing.
- **Transitions:** an ordered list per state, where the first match wins. A transition is `{ to: stateId | "$succeeded" | "$failed", when?: Guard }`, and a transition without `when` always matches, so it works as the default. Guards are structured data, never evaluated strings:
  - `{ kind: "status", is: "completed" | "failed" }` checks the agent outcome.
  - `{ kind: "output", field, op: "eq" | "neq" | "truthy" | "falsy" | "contains", value?: string | number | boolean }`. `contains` matches a substring in a string or an element in a `string[]`.

  If a completed visit matches no transition, the run fails with `No transition matched from <id>`. A failed agent visit, meaning an agent error or an unmet output contract, takes only transitions whose guard is `status: failed`. Otherwise the run fails.
- **Visit cap:** entering a state for the `maxVisits + 1`th time fails the run with `State <id> exceeded <n> visits`.
- **Approval state** (`kind: "approval"`): shows its rendered `message` and waits, with the run status `waiting-approval`. The user approves or rejects, with an optional note. The state's outputs are fixed as `approved: boolean` and `note: string`, and its transitions use guards on them.
- **Run snapshot:** a run stores a copy of the Flow definition taken at start, so editing a Flow never changes runs already in progress.
- **Recovery:** on app start, any visit still `running` is marked `failed` with error `Interrupted by app restart`, and its run becomes `failed`. Its session may still exist and can be opened. **Resume from state** appends a new visit for a chosen state to the same run and continues. It works on `failed` and `cancelled` runs, and is how both restart recovery and manual retries are done.
- **Cancel** stops the active session through the host and marks the visit and the run `cancelled`.
- **v1 runs one state at a time.** Separate runs can run concurrently, each in its own worktree.
- **Starter template:** "Fix an issue" (triage → implement → test → review, with a loop back to implement) ships as `STARTER_FLOWS[0]` so users have something working to copy.

## Review Focus

1. **A loop that never converges** (test keeps failing). The `maxVisits` cap and the 50-step cap must both end the run with a readable error (Task 4 tests).
2. **An agent that forgets or mangles the JSON block, or writes JSON inside prose.** Only the last ```json block counts. One retry in the same session, then a clear failure (Task 2 and Task 4 tests).
3. **The app quits while a state is running.** Recovery marks it failed, and Resume from state re-runs it in the same worktree (Task 4 test, Task 7 manual check).
4. **A Flow edited or deleted while a run is active.** The run keeps its snapshot. Deleting is refused while a run is `running` or `waiting-approval` (Task 3 test).
5. **A binding to a state that hasn't run yet**, on the first pass through a loop. This is a validation-time warning only when the binding is non-optional *and* unreachable before the binding state. At runtime it is the explicit error above (Task 1 and Task 4 tests).

export type FlowRunStatus = "running" | "waiting-approval" | "succeeded" | "failed" | "cancelled";
export type VisitStatus = "running" | "waiting-approval" | "completed" | "failed" | "cancelled";
export type FlowVisit = { id: string; runId: string; seq: number; stateId: string; status: VisitStatus; prompt?: string; sessionId?: string; outputs?: Record<string, OutputValue>; error?: string; retried?: boolean; note?: string; startedAt: number; finishedAt?: number };
export type FlowRun = { id: string; flowId: string; flow: Flow /* snapshot */; status: FlowRunStatus; inputs: Record<string, string>; worktreeCwd?: string; currentStateId?: string; error?: string; createdAt: number; finishedAt?: number };

export type LaunchRequest = { harness: HarnessId; model: string; cwd: string; worktreeCwd?: string; title: string; prompt: string };
export type AgentOutcome = { status: "completed" | "failed" | "cancelled"; text: string; error?: string };
export type FlowHost = {
  launchAgent(req: LaunchRequest): Promise<{ sessionId: string; worktreeCwd?: string; outcome: AgentOutcome }>;
  followUp(sessionId: string, prompt: string): Promise<AgentOutcome>;
  cancel(sessionId: string): Promise<void>;
  saveRun(run: FlowRun): Promise<void>;
  saveVisit(visit: FlowVisit): Promise<void>;
  onTransition?(run: FlowRun, prev: FlowRunStatus | undefined): void;   // Board hooks in here later
  now(): number; newId(): string;
};

export const MAX_RUN_STEPS = 50;
export class FlowRunner {
  constructor(host: FlowHost);
  start(flow: Flow, given: Record<string, string>): Promise<{ ok: true; run: FlowRun } | { ok: false; errors: string[] }>;
  resolveApproval(runId: string, approved: boolean, note: string): Promise<void>;
  cancel(runId: string): Promise<void>;
  resume(run: FlowRun, visits: FlowVisit[], stateId: string): Promise<void>;
  recover(runs: FlowRun[], visits: Record<string, FlowVisit[]>): Promise<FlowRun[]>;   // called once at startup
  whenSettled(runId: string): Promise<FlowRun>;   // resolves at the first status other than "running" (waiting-approval or terminal)
}
```

How the loop runs:
- `start` validates the Flow (an `errors` result refuses to start) and resolves inputs. It saves a run with `status: "running"` and the definition snapshot, then drives the loop **without awaiting completion**. It returns as soon as the run is saved.
- **Each step:**
  1. Check the caps. If they pass, render the brief.
  2. Save a `running` visit with `prompt` = rendered brief + contract footer.
  3. Call `launchAgent`, passing `run.worktreeCwd`. If it's unset, the host creates a worktree, and the runner stores the returned `worktreeCwd` on the run.
  4. Parse the outputs. If that fails, call `followUp` once with `retryPrompt` and set `retried`.
  5. Save the visit, call `selectTransition`, and move to the next state or to a terminal.
- **An approval state** saves a `waiting-approval` visit and sets the run to `waiting-approval`, then returns. `resolveApproval` completes the visit with `{approved, note}` and continues.
- **On every run status change**, call `saveRun`, then `onTransition(run, prev)`.
