# Flows Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Users define reusable, parameterized multi-step Flows. Each step can run on any harness/model, and a Flow runs deterministically through the existing orchestration engine without a lead agent planning it.

**Architecture:** A Flow is a stored template: params plus steps with `dependsOn`. Running it interpolates `{{param}}` values, validates the step graph, and converts it to an `OrchestrationProposal`. That proposal goes to a new `orchestrator.startHeadless()`, which reuses the engine's scheduler, worktrees and write-scope isolation. In headless mode the app itself is the lead: no lead session, no supervise prompt, and step results are accepted either automatically or by the user in the Flows UI. Before each step dispatches, the results of its dependencies are appended to its prompt.

**Tech Stack:** Rust + rusqlite (JSON-blob rows, the same pattern as `automations.rs`), React 19 + TS, Vitest.

**Spec:** Conversation decisions from 2026-10-23 ("custom multi-step process … each step can use any agent … deterministic output") and the Design Decisions below.

## Global Constraints

- Storage follows `automations.rs`: `ensure_tables(conn)` is called from the end of `session_store::migrate` (next to `crate::automations::ensure_tables`). **Do not** add a numbered migration.
- Commands take `store: State<'_, SessionStore>`, return `Result<_, String>`, and emit `"rebase:flows-changed"` after writes.
- Step limits are the same as orchestration: 1–40 steps. Paths in `files` must not contain `..`. Harness/model must be in the available choices.
- Param names match `^[a-zA-Z_][a-zA-Z0-9_]{0,39}$`. Interpolation syntax is `{{ name }}` (whitespace inside the braces is allowed).
- Commits carry no Claude or co-author attribution. Run a local Cubic review before pushing or opening a PR.

## Design Decisions (my calls, flag if wrong)

- **Headless mode is a new engine entry point.** `startApproved` requires a live lead session and submits a "supervise" prompt to it, which is the opposite of deterministic. `startHeadless` uses a synthetic lead id `flow-run:<runId>` and skips `host.session(leadId)` and `host.submit`.
- **A missing param is an error, never an empty string.** Interpolation returns the list of missing names, and the run dialog blocks until they're filled.
- **Data flow is prompt context, not structured variables.** A step's dispatched prompt is its own prompt, followed by `\n\n## Results from earlier steps\n` and one `### <title>\n<result>` per direct dependency. Each result is truncated to 8,000 chars with the marker `\n…[truncated]`. Structured outputs (step results as named variables) are out of scope for v1.
- **Review mode per Flow:** `"auto"` accepts every completed step. `"manual"` puts the run in `awaiting-review` when steps finish, and the user accepts or rejects each one in the run view (this maps onto the engine's existing `accepted` flag).
- **A failed step blocks its dependents.** The run ends `failed` once nothing else can run. There are no retries in v1; a "Re-run" button starts a fresh run with the same inputs.

## Review Focus

1. Cyclic or self-referencing `dependsOn` would deadlock the scheduler forever. `validateFlow` must reject it (Task 1 test).
2. App restart mid-run: a `flow_runs` row stuck in `running` with no live engine run. On load, runs whose engine run no longer exists get marked `failed` with error `"Interrupted by app restart"` (Task 3 test).
3. A `{{param}}` inside a step's `files` scope as well as its prompt is interpolated too, and `..` is rejected after interpolation, not before (Task 1 test).
4. Deleting a Flow while it has runs cascades to delete its runs. Deleting a Flow that has a *running* run is refused with `"Flow has an active run"` (Task 2 test).
5. An automation whose `flowId` points at a deleted Flow is recorded as a `failed` run with error `"Flow not found"` and doesn't crash the scheduler loop (Task 5 test).

### Task 1: Flow model (types, validation, interpolation, proposal bridge)

**Files:**
- Create: `src/features/flows/model/flow.ts`, `src/features/flows/model/flow.test.ts`

**Interfaces:**
- Consumes: `OrchestrationProposal`, `ProposedTask`, `OrchestrationChoice` from `src/features/orchestration/model/orchestrationPlan.ts`; `HarnessId`.
- Produces:

```ts
export type FlowParam = { name: string; label: string; required: boolean; default?: string };
export type FlowStep = { id: string; title: string; prompt: string; harness: HarnessId; model: string; files: string[]; dependsOn: string[] };
export type FlowReview = "auto" | "manual";
export type Flow = { id: string; name: string; description: string; cwd: string; params: FlowParam[]; steps: FlowStep[]; review: FlowReview; maxWorkers: number; createdAt: number; updatedAt: number };
export type FlowStepRunStatus = "queued" | "running" | "completed" | "failed" | "blocked" | "cancelled";
export type FlowRunStatus = "running" | "awaiting-review" | "succeeded" | "failed" | "cancelled";
export type FlowRun = { id: string; flowId: string; status: FlowRunStatus; inputs: Record<string, string>; leadId: string; steps: Record<string, { status: FlowStepRunStatus; result?: string; error?: string; accepted?: boolean }>; error?: string; createdAt: number; finishedAt?: number };

export function validateFlow(flow: Flow): string[];                  // [] = valid; human-readable messages
export function interpolate(text: string, inputs: Record<string, string>): { ok: true; text: string } | { ok: false; missing: string[] };
export function resolveInputs(flow: Flow, given: Record<string, string>): { ok: true; inputs: Record<string, string> } | { ok: false; missing: string[] };
export function flowToProposal(flow: Flow, inputs: Record<string, string>, choices: OrchestrationChoice[], leadId: string): { ok: true; proposal: OrchestrationProposal } | { ok: false; errors: string[] };
export function dependencyContext(step: FlowStep, steps: FlowStep[], results: Record<string, string>): string;  // "" when no deps
```

### Task 3: Headless orchestration and the flow runner

**Files:**
- Modify: `src/features/orchestration/model/orchestration.ts` (add `startHeadless`, a `beforeDispatch` hook, and skip lead-only paths when `run.headless`)

**Interfaces:**
- Produces on `Orchestrator`:

```ts
startHeadless(leadId: string, proposal: OrchestrationProposal, opts: {
  autoAccept: boolean;
  beforeDispatch: (task: ProposedTask, completed: Record<string, string>) => string;  // returns the prompt to send
}): Promise<void>;
acceptTask(leadId: string, taskId: string, accepted: boolean): void;   // reuse existing accept path if one exists
```

  `OrchestrationRun` gets an optional `headless?: true`. When it's set, every `host.session(leadId)` / `host.submit(leadId, …)` / lead-notification call is skipped, and the run finishes when no task is queued or running.
- Produces in `flowRunner.ts`:

```ts
export function startFlowRun(flow: Flow, given: Record<string, string>, deps: FlowRunnerDeps): Promise<{ ok: true; run: FlowRun } | { ok: false; errors: string[] }>;
export function syncFlowRun(run: FlowRun, engine: OrchestrationRun | undefined): FlowRun;   // pure: maps engine state → FlowRun
export function recoverInterruptedRuns(runs: FlowRun[], liveLeadIds: Set<string>): FlowRun[]; // pure
export type FlowRunnerDeps = { orchestrator: Pick<Orchestrator, "startHeadless" | "subscribe" | "run">; choices: OrchestrationChoice[]; saveRun: (r: FlowRun) => Promise<void>; now: () => number; newId: () => string };
```

  Status mapping in `syncFlowRun`:
  - TaskStatus `completed`→`completed`, `failed|interrupted`→`failed`, `blocked`→`blocked`, `cancelled|cancelling`→`cancelled`, otherwise `queued`/`running`.
  - FlowRun status: an engine run `stopped` → `cancelled`. Any step failed with nothing running → `failed`. Every step completed with review `manual` and any step not yet `accepted` → `awaiting-review`. All completed and accepted → `succeeded`.
