# Board #174 C4: codebase map (2026-10-26)

Paths are relative to the repository root.

I covered all seven areas for both apps, plus board-store. In short: today both apps search title and `#N` only, the description is never searched, and the filter is three sets (projects, labels, priority). Neither app keeps any linked-work state on cards, so "running / failed / needs review" has no data behind it yet. There is no views table, and nothing is virtualised.

## 1. Current search and filter

**Native**
- The filter type is at `crates/gespan-gpui/src/board.rs:123`: `pub(crate) struct Filter { pub projects: BTreeSet<String>, pub labels: BTreeSet<String>, pub priorities: BTreeSet<u8> }`. `len()` sums the three sets (`:130`).
- `BoardView` fields: `filter` and `filter_open` (`board.rs:179-180`), `search: Entity<Input>` (`:178`, created at `:244` as `Input::field("Search tasks", …)`). Filter state is in memory only and is never saved.
- Matching lives in `crates/gespan-gpui/src/board/header.rs`:
  - `query(&self, cx) -> String` trims and lowercases the search text (`:74`).
  - `card_visible(&self, card: &Card, cx: &App) -> bool` (`:83`).
  - `card_matches(&self, card: &Card, query: &str) -> bool` (`:88-108`). `#N` must equal the card number exactly; anything else is a case-insensitive title substring. Within one set any value matches (OR); across sets all must hold (AND). A card with no priority counts as 0.
  - **The description (`card.body`) is not searched.**
- `count_label` shows "shown/total" while narrowing (`:111`).
- The filter popover is `render_filter` (`:320-460`): Projects, Labels and Priority checkbox rows plus "Clear filters". The column applies the filter at `column.rs:58`.

**Tauri**
- `src/features/board/model/boardFilter.ts`:
  - The type is `BoardFilter = { projects: Set<string>; labels: Set<string>; priorities: Set<number> }` (`:3`), with `EMPTY_FILTER` (`:9`) and `filterCount` (`:16`).
  - `matchesCard(card: Pick<BoardCard,"number"|"title">, extras: CardExtras|undefined, query: string, filter: BoardFilter): boolean` (`:28-50`) uses the same rules as Native. **The description is not searched.**
  - `pruneFilter` (`:62`) drops labels and projects that no longer exist. `fullIndex` (`:85`) maps a drop index among visible cards back to an index among all cards.
- `src/features/board/ui/BoardFilter.tsx`: `BoardFilterMenu({filter, labels, projects, onChange})` (`:41`), a `MenuButton` with checkbox items and "Clear".
- `BoardView.tsx`:
  - Filter state is `useState<BoardFilter>(EMPTY_FILTER)` (`:236`) and is reset when the board changes (`:401`).
  - Pruning happens at `:465`. `matches` / `shownDetail` (`:469-480`) filter `detail.cards` before handing them to `KanbanBoard`.
  - The search input is at `:1124-1136`; Escape clears it. The menu is mounted at `:1139`.

## 2. Data available per card

| Data | Native | Tauri |
|---|---|---|
| Priority, due, projects, labels, subtask and comment counts | One board-wide call, `service.extras(board_id)` (`board.rs:455`), into `extras: HashMap<String, CardExtras>` (`:174`) | One board-wide call, `getCardExtras` → `board_card_extras` (`model/board.ts:263`, `src-tauri/src/board.rs:486`), in `refresh` (`BoardView.tsx:345`) |
| `created_at` / `updated_at` | On `Card` (`crates/board-store/src/lib.rs:105-106`) | On `BoardCard.createdAt` / `updatedAt` (`board.ts:40-41`) |
| Start date, estimate, completed | Per card only: `card_meta(card_id)` (`meta.rs:45`) | Per card only: `board_card_meta` (`board.ts:439`) |
| Custom field values | Per card only: `field_values(card_id)` (`fields.rs:181`), loaded in the drawer (`detail.rs:378-379`) | Per card only: `board_card_field_values` (`board.ts:490`), used in `CardWorkSections.tsx:388` |
| Field definitions | Per board: `list_fields(board_id)` (`fields.rs:94`) | Per board: `listFields` (`board.ts:476`) |

- `CardExtras` (`meta.rs:29`) has only priority, due_at, projects, labels and counts. It has **no** start_at and no field values.
- **There is no board-wide fetch for start date or custom field values.** You would need a new batch query, for example extend `card_extras` (`meta.rs:409`, which already uses a `card_id IN (scope)` pattern) or add `board_field_values(board_id)`.

**Linked-work state is not stored anywhere for a card in either app.**
- **Native:** `gespan_core::board::linked_turns::LinkedTurns` (`linked_turns.rs:24`) and `board/turns.rs` (`turn_started` `:116`, `turn_settled` `:138`, `dispatch` `:233`) only turn `LinkedWorkEvent {Started, Completed, Failed}` (`auto_move.rs:7`) into auto-moves and activity rows. The card's link label is just `LinkLabel::{Found(title), Missing}` (`board.rs:70`, built at `:520-545`), with no running or failed state.
- **Tauri:** `createLinkedTurns` (`linkedTurns.ts:45`, held in `App.tsx:1830`) also only emits events. The live state is `BoardLinkTarget.status?: "running"|"completed"|"failed"` (`boardFormat.ts:25`), built in `App.tsx:13968-13995`:
  - A session is "running" if it is in `busySessionKey`, otherwise "completed".
  - A pilot is "running" if its `pilotRail` state is not idle.
  - **"failed" is never set there.** It is shown as a dot in `BoardCardItem.tsx:38,204`.
- **"Needs review"** can only be inferred today from the card being in a column with `role = "review"`.
- Persisted "failed" would have to come from `board_activity` rows written by the linked-turn events (the activity log, `ops.rs`). Otherwise a new column or table is needed.

## 3. board-store: views and migrations

- **There is no views table and no query engine.** `views.rs` does not exist, and the store has no sort or filter SQL beyond `ORDER BY position`.
- Places that could hold views without a migration:
  - `board_settings` (`schema.rs:146-152`; Rust API `settings.rs:9,27,58`) is one row per board with `run_with`, `write_back`, `ticket_status_changes`, `auto_move_json`. A `views_json` column would follow the same pattern as `auto_move_json`.
  - The app-wide key/value `Database::setting` / `save_setting` (`crates/gespan-core/src/store.rs:192,207`), as used for `board-card-open` (`header.rs:15,469`). Native-only, and not in board-store.
- How migrations work today:
  - `schema.rs:4` sets `pub const VERSION: i64 = 3`.
  - `ensure_tables` (`schema.rs:158`) returns early when `migrate::version >= VERSION`, otherwise calls `migrate::run`.
  - `migrate::run` (`migrate.rs:26`) takes an IMMEDIATE transaction, re-checks the version, and runs `V2_TABLES` and `V3_TABLES` (all `CREATE TABLE IF NOT EXISTS`).
  - It then adds `V3_COLUMNS` through `column_exists` + `ALTER TABLE` (`:34-40`), copies the old native data, and rewrites `board_schema`.
- To add a v4 table: set `VERSION = 4`, add a `V4_TABLES` const (for example `board_views(id, board_id, name, position, filter_json, sort_json, layout_json, …)`), and add its `execute_batch` (plus any new columns in a `V4_COLUMNS` list) to `run`. This works because everything is idempotent. The function is still written as one linear v2→v3 pass, so it should be reorganised into steps per version.
- Bulk writes already exist: `archive_cards` (`meta.rs:274`) and `move_cards` (`ops.rs`), exposed in Native as `archive_many` / `move_many` (`gespan-core/src/board/extras.rs:83,114`, used in `board/quick.rs:282,331`). There is no bulk set-priority or set-labels, and no bulk delete.

## 4. Existing keyboard shortcuts

**Native**
- `board.rs:56` `bind` → `new_card::bind` (`new_card.rs:28-37`) binds `cmd/ctrl-n` → `OpenNewCard` and `cmd/ctrl-enter` → `SubmitNewCard` in the `"Board"` key context (`board.rs:1222`).
- `on_key` (`board.rs:954-982`) handles Escape only. It closes, in order: keyboard lift, new-card modal, composer, filter, open-in menu, switcher, rename, menu, drawer sub-layer, full page, drawer, then emits `Event::Close`.
- `card_key` (`keyboard.rs:60-102`), wired up in `card.rs:129`, ignores modified keys. Enter opens card actions, Space lifts, arrows move focus. While a card is lifted, Space/Enter drop it, arrows move the target, and other keys are swallowed.
- Header buttons use `presses` (Enter/Space) (`header.rs:29`).
- **Bare N, /, E and Delete are not bound** on the board, so there is no conflict. They would need guarding while an `Input` is focused (search, composer); the `Composer` context binds backspace/delete in `input.rs:94-95`.
- Note: Native Enter opens the actions menu, not the drawer; a click opens the drawer.

**Tauri**
- `BoardView.tsx:1043-1061` `onKeyDownCapture` handles only Cmd/Ctrl+N (no Shift or Alt) → `setNewCardOpen(true)`.
- The search box Escape clears the query (`:1130`).
- `KanbanBoard.tsx:95` `KEYBOARD_CODES = { start: ["Space"], cancel: ["Escape"], end: ["Space","Enter"] }` comes from the dnd-kit keyboard sensor, which moves cards with arrows while lifted.
- `KanbanCard.tsx:42-52`: Enter → `onOpen(card)`.
- Drawer Escape: `CardDetail.tsx:265-268,385` (full page → drawer → close).
- **Bare N, /, E and Delete are free.** Arrow-key focus movement between cards is not implemented in Tauri; arrows only work during a dnd-kit lift.

## 7. Performance

- **Native:** every matching card in each column is rendered as a child of a scrolling div (`column.rs:58` filter, `:112` `render_card`, `:259-264` `overflow_y_scroll().children(body)`). Each render calls `card_matches` once per card, and `count_label` re-filters again for each column. There is no virtualisation. Each card also gets a `FocusHandle` (`card_focus`) and an `AnchorSlot`.
- **Tauri:** `KanbanColumn.tsx:140-146` maps every card into a dnd-kit `SortableContext`. There is no virtualisation. `shownDetail` copies and filters on every change to query, filter or extras.
- **1,000-card target:** this is phase C6 in `docs/superpowers/plans/2026-10-25-board-174.md:417` ("1,000-card performance pass in both apps"); C4 is at `:415`. Rendering List and Table views with 1,000 rows will need `uniform_list` in Native and a windowing approach in Tauri. Tauri has no such library today, so that means either extending the `useDiffViewport` approach or adding a dependency.
