# Board #174: codebase maps (2026-10-25)

Reference for implementers of `2026-10-25-board-174.md`. Paths are relative to the repository root; line numbers are as of the planning commit.

I found everything you asked for. A few points affect the plan directly:
- **No schema versioning for board tables.** Both apps create them with `CREATE … IF NOT EXISTS`, and the two definitions are identical.
- **The storage logic differs on one point.** gespan-core takes the SQLite write lock before reading what it changes. Tauri reads first and then opens a deferred transaction. Pick the gespan-core version for the shared crate.
- **There are two separate Cargo workspaces.** That limits how `board-store` can declare rusqlite (see 3c).
- **The CI path filter misses `src-tauri/src/board.rs`.** A change to Tauri's board DDL won't trigger the native workflow that runs the contract tests.

**Migration mechanism**
- Board tables have none: no `user_version`, no version row, idempotent `IF NOT EXISTS` only.
- Tauri: `migrate()` (`src-tauri/src/session_store.rs:708`) keeps a `schema_migrations(version INTEGER PRIMARY KEY, applied_at INTEGER NOT NULL)` table with versions 1–19. After those steps it unconditionally calls `crate::board::ensure_tables(conn)?` (session_store.rs:1034). That call is not inside a versioned block.
- gespan-core: `Store::open_gespan` (`store/shared.rs:218-262`) applies `shared_schema.sql` only to a brand-new file, and that file contains no board tables. The board tables come only from `board::Service::open` → `ensure_tables` (mod.rs:919).

**Logic differences** (diff of mod.rs:106-896 against board.rs:85-867)
- gespan-core's `write_tx` (mod.rs:414) is `Transaction::new_unchecked(conn, TransactionBehavior::Immediate)`. Every write opens it before its lookups (`get_card`, `get_column`, `board_exists`).
- Tauri uses `conn.unchecked_transaction()` (deferred) and does the lookups on `conn` before the transaction. This applies to `create_board`, `create_column`, `update_column`, `move_column`, `delete_column`, `create_card`, `update_card`, `move_card`, `link_card`, `delete_card` and `record_card`.
- Everything else is identical: constants, validation, error strings, SQL. `validate_id` and `now_millis` are local in mod.rs:13-29; Tauri imports them from `session_store.rs:2131/2142`.
- Shared constants (both files): `MAX_NAME=200`, `MAX_TITLE=500`, `MAX_BODY=1_000_000`, `MAX_ACTIVITY=500`, `ROLES=[todo,doing,review,done]`, `LINK_KINDS=[session,pilot,flow-run]`, `ACTORS=[user,system]`, `RECORD_KINDS=[started,completed,failed]`, `DEFAULT_COLUMNS` = Backlog/todo, In Progress/doing, Review/review, Done/done.

## 3. Database opening and crate wiring

**a. The file is `gespan.db` in both apps.**
- Tauri: `init_with` → `app_data_dir()/gespan.db` (`session_store.rs:92`).
- `SessionStore{conn:Mutex<Connection>, read_conn:Mutex<Option<Connection>>}` (32). `open` (38-56) runs `PRAGMA foreign_keys = ON; PRAGMA journal_mode = WAL;`, then `migrate()` (which includes board `ensure_tables`).
- The second, read-only connection gets `PRAGMA query_only = ON; PRAGMA busy_timeout = 5000;`. The write connection has no explicit busy_timeout, so it runs on rusqlite's default.
- Board commands use the single mutex-guarded write connection via `lock_conn()` (69).

**b. Native app**
- `gespan_core::store::gespan_database()` (`store/gespan_import.rs:17-32`) → `…/dev.gespan.desktop/gespan.db`. It can be overridden with `--gespan-db`/`--dev-data` (`crates/gespan-gpui/src/main.rs:261-330`).

  - the turns worker thread opens a second Service at `board/turns.rs:36`, installed from `shell.rs:1087-1088`.

**c. rusqlite and workspaces**
- rusqlite matches in both builds: `0.40.2`, `default-features = false`, features `["bundled","hooks"]`.
  - `src-tauri/Cargo.toml:40` declares it directly.
  - The gpui workspace declares it in `[workspace.dependencies]` (`crates/gespan-gpui/Cargo.toml:99`). gespan-core uses `rusqlite.workspace = true` (core Cargo.toml:11), and gespan-gpui uses it as a dev-dep only (62).
  - Both lockfiles resolve 0.40.2 (`Cargo.lock:4362`, `crates/gespan-gpui/Cargo.lock:5653`).
- Root `Cargo.toml`:
  - `members = ["src-tauri","crates/mobile-link","crates/keep-awake","crates/gespan-redact","crates/tracker-secrets"]`
  - `exclude` includes `crates/gespan-core` and `crates/gespan-gpui`.
  - `[workspace.dependencies]` has only serde, serde_json and thiserror. **There is no rusqlite there.**
- The gpui workspace (`crates/gespan-gpui/Cargo.toml:87-99`) has `members = [".", "../gespan-core"]`. gespan-core sets `workspace = "../gespan-gpui"` (core Cargo.toml:2).
- How the existing shared crates are wired:
  - `tracker-secrets` and `gespan-redact` are root-workspace members with **hard-coded** `version/edition/license` and no `.workspace = true` inheritance. That is what lets them build under both workspaces.
  - gespan-core pulls them in as plain path deps: `gespan-tracker-secrets = { path = "../tracker-secrets" }` (27) and `gespan-redact = { path = "../gespan-redact" }` (49). Dev-deps enable the `testing`/`fixtures` features (74, 77).
  - src-tauri depends on `gespan-tracker-secrets` (`src-tauri/Cargo.toml:21`, dev `features=["testing"]` at 85) but not on gespan-redact. gespan-gpui depends on gespan-redact (12).
- Consequence for `board-store`: it must spell rusqlite out as `0.40.2` / bundled+hooks / no defaults instead of using `.workspace = true`, and avoid workspace inheritance. Otherwise it won't build in both workspaces.
- Its other deps would be `uuid` (v4), `serde`, and `chrono` if extras move in. src-tauri has uuid and serde but not chrono.
- CI: `.github/workflows/native.yml:8-46` lists paths that trigger the native tests. It includes `crates/tracker-secrets/**` but not `crates/gespan-redact/**` or `src-tauri/src/board.rs`. The new crate needs adding there.

  - `command.envs(...)` (`provider.rs:1443`).
  - Codex `configure_codex` (`:1448`).
  - Claude `--mcp-config {"mcpServers":{"gespan_visual":…}}` (`:1494-1499`).
  - ACP `mcpServers` in `session/new` and `session/load` (`provider/acp.rs:240`, `:254`, `:559`).
  - Adding a second server (e.g. `gespan_ticket`) means extending each of these. The cleaner route is to generalise `mcp_server`/`acp_servers`/`configure_codex` to return several servers.

## 4. How tool calls appear in the transcript

- **Event handling:** `Event::Tool(ToolCall)` in `runtime.rs:671-689` serialises the `ToolCall` (`crates/gespan-core/src/tool.rs:18`, fields `id,name,input,output,state,panel,display`) into a `"tool"` row.
- **Names:**
  - Codex MCP calls are renamed to `"{server}:{tool}"`, e.g. `gespan_visual:visual_show` (`provider.rs:1238-1239`).
  - Claude passes its raw name through (`mcp__gespan_visual__visual_show`). Nothing in the repo handles `mcp__` specially.
- **Rendering:**
  - `ToolCall::summary()` (`tool.rs:99`) calls `presentation::present` (`tool/presentation.rs:71`).
  - An unknown name falls through to `action = call.name` (`:241-249`), and the target is usually empty for object inputs (`:262-271`).
  - So an MCP visual or ticket tool shows its raw name as the label. The row is drawn in `crates/gespan-gpui/src/transcript/tools.rs:48-72`.
- **The published visual itself** is a separate `"visual"` row, rendered by `transcript/visuals.rs:18` (`visual_row`).
- **Friendly ticket labels** would go in `present()` (name match near `:152-160`).
